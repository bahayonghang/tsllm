# 前端加载影响与拆分收益评估报告

日期：2026-09-30（America/Chicago）。固定提交：`e9ce26a7bd1a4ed67cd30d257354e7345c44dec1`。评估分支：`codex/frontend-load-assessment`。本报告仅提出方案建议，产品落地、提交和归档不在本次授权内。

## 1. 决策摘要

本报告以 `recovery-r1` 的 90 个主观测与 3 个补充旅程为最终数值依据。该修订已修复 B1/B2 恢复按钮的真实点击，并通过前端门槛、双视口行为与实际模块恢复复验。当前样本全部有效，测量失败和重试均为 0。原始完整报告与复算保存在 `evidence/report/original-report.md` 和 `original-recomputed.json`，不与新修订合并。

建议将 B1 作为后续产品拆分的候选，当前 B2 不建议采用。B1 冷 `/runs` 资产从 2,419,860 B 降至 1,094,078 B，减少 54.79%；功能就绪中位数由 303.8 ms 降至 225.0 ms，减少 78.8 ms。代价是资产 URL 从 1 个增至 9 个、首次表单中位数增加 13.0 ms，完整访问传输增加 15,384 B（0.62%）。产品实施仍需另行授权。

B2 相对 B1 的冷入口多 2,450 B、9 个资产 URL，没有额外入口节省。首次表单就绪中位数由 197.1 ms 增至 419.5 ms，完整访问多 19,169 B（0.77%）。B1/B2 冷入口区间以及三个方案热入口区间重叠，不将微小中位数差异解释为稳定提速。时间结论仅覆盖本机 Edge、合成夹具、环回网络和既定观察器。

原始 90 个正式观测、6 个 B0 试测和 3 个补充旅程保留。恢复修订另有 2 个 B0 冷/热试测，不计入 90 个主观测。最终矩阵中 B2 预测详情的 2,439.7 ms 较高样本保持有效并参与统计，原因未查明。正式门槛、数值/HTTP/绘制采集/范围独立检查与服务清理均已有通过证据；本报告的最终独立审阅由 verification.md 统一记录。

## 3. 测量方法与复算口径

### 3.1 矩阵和就绪条件

主矩阵为 3 个方案 × 6 个场景 × 5 次，共 90 个观测。轮次顺序为 B0/B1/B2、B1/B2/B0、B2/B0/B1、B0/B1/B2、B1/B2/B0。每个首次导航观测从独立的入口状态开始。原始 6 个 B0 试测、恢复修订 2 个 B0 试测和每修订每方案 1 个完整旅程分别保留，均不计入对应主矩阵。B0 资产虽未变化，最终矩阵仍与 B1/B2 同期交替重测，未复用旧 B0 时间。

| 场景标识 | 起点与终点 | 计时起点与就绪条件 |
| --- | --- | --- |
| cold-runs | 直接打开 `/runs` | 文档导航起点至真实列表、数据与操作控件可用，并连续两个动画帧成立 |
| warm-runs | 同一上下文再次打开 `/runs` | 重新载入文档起点至同一列表条件；另保留先前冷入口资源 |
| first-form | `/runs` → `/runs/new` | 可信 UI click 至真实 schema 表单可用；随后另测真实预览按钮 |
| first-compare | `/runs` → 含 5 个作业的 `/compare` | `history.pushState` 与 `popstate` 导航至指标、警告及实际图表就绪；标为程序化路由导航 |
| first-dataset | `/datasets` → 合成数据集详情 | 可信 UI click 至元数据、运行段与曲线 Canvas 就绪 |
| first-forecast | `/runs` → 合成预测详情 | 可信 UI click 至结果图、上下文与预测请求完成，且对应系列有数据 |

图表观察器使用现有 React ECharts 实例，检查 finished、最终尺寸、数值系列、调度完成和非空彩色像素。已完成图表的像素扫描结果保留至下一次 rendered 事件。就绪时间包含观察器与连续两帧成本；不以 load、首个文字或工具响应时间替代功能就绪。

恢复修订统一使用 `paint-collection-r1` 收集文档绘制条目。原生 FCP 条目可能晚于第二个就绪动画帧发布，原始 B0 FCP 缺失已确认为收集时序问题；浏览器支持 paint API。修订保留原就绪终点及 resources/navigation/longTasks 快照，将原 paint 数组保存在 `paintAtReady`。随后读取同一文档的原生 Performance Timeline，并按需等待 buffered paint observer，最长 1,000 ms，再允许导航、刷新或关闭上下文。新增等待单独记为 `paintCollection.waitMs`，不加到功能就绪 duration，不把 FCP 截断到就绪终点。

三个方案使用相同冻结脚本和收集策略，每条新记录含脚本 SHA-256 与 instrument revision。原始矩阵不回填 FCP。该修订通过 8 项确定性检查，B0 试测实际取得三个文档阶段 FCP。最终 90 个主观测与 3 个旅程合计 108 个独立文档、213 个就绪快照，全部 `observed`。213 包含 195 个 stages 快照（主矩阵 165、旅程 30）及 18 个独立 preview 快照（主矩阵 15、旅程 3），不能解释为 213 个独立 FCP 样本。冷/热目标六组共 30 个文档的 FCP 为 30/30，每组 5/5。

33 个快照在原就绪时没有 FCP，补充收集后取得；1 个快照的原生 FCP 时间确实晚于就绪终点，按实际时间保留。额外收集等待为 0–6.8 ms，未加到就绪 duration。没有 timeout、unsupported 或 error。108 个独立文档由主矩阵 90 个入口、15 次 warm 重载与 3 个旅程入口组成。细节见 `evidence/measurement/recovery-r1/instrument/README.md`、`pilot-review.json` 与 `evidence/review/recovery-r1-paint-review.json`。

表单预览先通过真实模板选择器应用合成配置，确认 Name、context_length=12、horizon=6，再计量“预览并提交”按钮至校验后模态框可用的时间。没有点击最终提交。完整旅程依次访问运行列表、表单与预览、混合对比、数据集列表/详情、预测详情、分类详情和系统页；中间返回列表的请求也保留。

### 3.2 缓存、HTTP 与资源

冷观测使用新 BrowserContext 并执行 `Network.clearBrowserCache`，HTTP cache 功能保持启用。冷态仅指浏览器 HTTP 缓存；操作系统、进程和代码缓存未声明为冷态。恢复修订 830 条冷入口资产响应均为 HTTP 200、无缓存命中标记，Content-Length 与对应产物一致。

恢复修订 1,205 条资产响应均无 Content-Encoding 和 Cache-Control，实际未压缩，encodedBodySize 与 decodedBodySize 相同。15 个热重载样本的资产 transferSize 均为 0；B0/B1/B2 分别有 5/45/90 条 `cache-reported-no-disk-flag`，无法确定具体缓存层。HTML、API 和资产各自保留传输成本。离线 gzip 估算不能作为该服务的实际传输量。证据见 `evidence/review/recovery-r1-http-review.json`。

报告区分以下口径。全部字节使用 B；1 kB=1,000 B，1 KiB=1,024 B。

- 构建总量：index.html 与全部输出资产的文件长度之和。逐文件 gzip 后再求和，禁止将目录拼接压缩。
- 资产集合：完整 URL 去重后的 JS/CSS 资产 body；本次构建资产均为 JS。HTML、favicon 与 API 另列。
- 实际传输：Resource Timing 的 transferSize 求和，保留重复请求；属于浏览器计量口径，不包含完整 TCP/IP 开销。资源条目数也包含缓存命中的浏览器条目，不能全数称为网络请求。
- 入口集合：入口就绪快照中的全部已完成资源，包括 HTML、modulepreload 与初始 lazy 路由。静态 HTML 闭包不能替代实际入口集合。
- 导航窗口：点击/路由导航至目标就绪期间开始且完成的请求。导航新增集合排除入口已出现 URL。
- 累计集合：目标就绪快照内全部已完成资源，包含入口就绪后至点击前的请求；不简单拼接两个窗口。不同响应长度的同一 URL 使用最大 body，实际 transfer 求和仍保留重复请求。
- 热场景累计：先前冷入口与当前热文档合并；热文档成本单独展示。

变化量为方案值减比较基准；相对变化为变化量÷基准×100%。基准为 0 时标为“—”，不计算无限百分比。时间变化使用各组中位数；n=5 的最小/最大值仅描述本组观测，不构成总体置信区间。所有统计从未舍入值复算，表格最后一步才取一位毫秒和两位百分比。

## 5. 收益、代价与建议

### 5.1 B0

B0 首次列表入口即取得全部页面依赖，首次表单与图表导航不再新增 JS 资产。B0 的单个 JS 超过现有构建警告阈值；警告只说明产物体积，不能直接证明页面加载慢。完整访问只需一个资产 URL，维护加载状态与模块失败的责任最少。

### 5.2 B1

B1 冷 `/runs` 的资产 body 减少 1,325,782 B（54.79%），总 transfer 减少 1,322,904 B（54.59%）。就绪区间为 219.0–246.2 ms，低于本组 B0 的 284.7–309.0 ms，支持报告本次环境的冷入口改善。热入口中位数仅减少 1.3 ms，区间重叠，不支持稳定提速结论。

B1 将资源成本推迟到首次功能访问。表单首次导航增加 631,422 B 新资产，中位数从 184.1 ms 增至 197.1 ms；两组范围有重叠。三个图表场景中位数分别增加 27.7、27.7、20.8 ms。入口到这些功能页的累计 transfer 仍比 B0 低 21.11%–28.27%。完整旅程加载全部 20 个 JS 资产，transfer 从 2,488,399 B 增至 2,503,783 B（+0.62%），资源条目从 40 增至 58。字节收益集中于访问部分页面的路径，完整访问会付出拆分与多请求成本。

完整旅程 API transfer 中，B1 比 B0/B2 少 949 B，对应分类 metrics 的重复读取少 1 次；API body 的完整 URL 并集仍相同。该传输差异单独保留，不归因为 JS 节省。完整旅程每方案只有 1 次，不能据此推断 API 请求频率的稳定变化。

预测详情的较慢有效样本必须保留。后续产品决策应根据运行列表占比、首次表单使用频率和完整访问比例判断收益；本任务没有这些实际使用频率，因此不计算加权用户收益。

### 5.3 B2

B2 冷入口比 B1 多 2,450 B 资产、9 个资产 URL 和 6,150 B 实际 transfer。就绪中位数只相差 2.6 ms，区间重叠。更细边界没有带来额外入口资源收益，却增加请求和状态处理责任。

B2 相对 B1 的首次表单增加 222.4 ms（112.84%）；对比、数据集详情和预测详情的中位数分别增加 265.9、278.0、276.9 ms。预测详情全部 5 个样本范围为 1,425.5–2,439.7 ms，较高值来自 `B2-first-forecast-s3-a1.json`，未删样或补采，原因未查明。虽然该预测路径的累计资产比 B1 少 198 B（0.01%），实际累计 transfer 仍多 4,102 B。完整访问比 B1 多 11,820 B 资产、19,169 B transfer 和 18 个资产 URL，不支持采用当前 B2。

功能模块在数据条件成立后才请求，存在额外模块获取与渲染阶段，具备增加串行等待的机制。当前实验没有对每个等待机制进行单独干预，无法把全部延迟差值归因于模块下载、某个包的解析或 React 调度；具体份额原因未查明。独立预览计时不包括首次加载表单和模板选择的成本，应单独解释。

建议后续如要实施，优先选择已修复恢复行为的 B1，并保留其加载中、显式重载、深链接和首次使用回归用例。当前 B2 不建议采用。决策同时考虑字节、首次功能成本、完整访问资源与维护复杂度；不以构建警告消失或任意百分比作为通过门槛。
