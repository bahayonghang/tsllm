# 前端加载影响与拆分收益评估报告

日期：2026-09-30（America/Chicago）。固定提交：`e9ce26a7bd1a4ed67cd30d257354e7345c44dec1`。评估分支：`codex/frontend-load-assessment`。本报告仅提出方案建议，产品落地、提交和归档不在本次授权内。

## 1. 决策摘要

当前数字对应 original 修订。后续 B1 可见检查发现真实恢复失败：模块文件恢复后，点击指向相同 URL 的原生链接仍停留在错误提示，没有重载文档。修复代理正在为 B1/B2 加入显式重载，新的 90 个主观测与 3 个旅程将写入 `evidence/measurement/recovery-r1/`。原始结果保留，不将旧修订数字作为修复后验收。

原始 B1 路由延迟加载明显减少冷启动运行列表所需的资产字节，并将表单和图表模块的获取推迟到首次访问。B1 是后续产品拆分的候选；最终建议须等待恢复行为修正、重新测量与可见检查。产品实施仍需另行授权。

当前 B2 在 B1 上增加六个功能边界，冷入口没有进一步的资源收益，首次表单和图表就绪时间增加，完整访问的资源和请求也增加。当前证据不支持采用 B2。时间结论仅覆盖本机 Edge、合成夹具、环回网络和既定就绪观察器。缓存复用时间的样本范围重叠，不能宣称稳定提速。

90 个正式观测、6 个 B0 试测和 3 个完整访问补充观测全部有效，没有测量重试。每个主矩阵组合有 5 个样本，未排除预测详情的长尾样本。正式门槛与数值独立检查已通过。B1/B2 可见验收及最终清理由主会话补充；这些项目完成前不宣称 AC1–AC6 全部完成。

### 3.2 缓存、HTTP 与资源

冷观测使用新 BrowserContext 并执行 `Network.clearBrowserCache`，HTTP cache 功能保持启用。冷态仅指浏览器 HTTP 缓存；操作系统、进程和代码缓存未声明为冷态。830 条冷入口资产响应均为 HTTP 200、无缓存命中标记，Content-Length 与方案产物一致。

1,205 条资产响应均无 Content-Encoding 和 Cache-Control。实际资产传输未压缩，encodedBodySize 等于 decodedBodySize。15 个热重载样本的资产 transferSize 均为 0；B0/B1/B2 分别有 5/45/90 条 `cache-reported-no-disk-flag`，无法确定具体缓存层。HTML 与 API 仍有传输成本。离线 gzip 估算不能作为该服务的实际传输量。

报告区分以下口径。全部字节使用 B；1 kB=1,000 B，1 KiB=1,024 B。

- 构建总量：index.html 与全部输出资产的文件长度之和。逐文件 gzip 后再求和，禁止将目录拼接压缩。
- 资产集合：完整 URL 去重后的 JS/CSS 资产 body；本次构建资产均为 JS。HTML、favicon 与 API 另列。
- 实际传输：Resource Timing 的 transferSize 求和，保留重复请求；属于浏览器计量口径，不包含完整 TCP/IP 开销。资源条目数也包含缓存命中的浏览器条目，不能全数称为网络请求。
- 入口集合：入口就绪快照中的全部已完成资源，包括 HTML、modulepreload 与初始 lazy 路由。静态 HTML 闭包不能替代实际入口集合。
- 导航窗口：点击/路由导航至目标就绪期间开始且完成的请求。导航新增集合排除入口已出现 URL。
- 累计集合：目标就绪快照内全部已完成资源，包含入口就绪后至点击前的请求；不简单拼接两个窗口。不同响应长度的同一 URL 使用最大 body，实际 transfer 求和仍保留重复请求。
- 热场景累计：先前冷入口与当前热文档合并；热文档成本单独展示。

变化量为方案值减比较基准；相对变化为变化量÷基准×100%。基准为 0 时标为“—”，不计算无限百分比。时间变化使用各组中位数；n=5 的最小/最大值仅描述本组观测，不构成总体置信区间。所有统计从未舍入值复算，表格最后一步才取一位毫秒和两位百分比。

## 5. 收益、代价与建议

### 5.1 B0

B0 首次列表入口即取得全部页面依赖，首次表单与图表导航不再新增 JS 资产。B0 的单个 JS 超过现有构建警告阈值；警告只说明产物体积，不能直接证明页面加载慢。完整访问只需一个资产 URL，维护加载状态与模块失败的责任最少。

### 5.2 B1

B1 的主要收益发生在首次列表入口与仅访问部分功能的路径。首次进入表单、对比、数据集详情或预测详情时，需要获取之前延后的模块，因此导航时间和新增资源应与入口收益一起评估。完整访问将加载全部 20 个 JS 资产，累计传输略高于 B0；拆分没有减少整个应用的功能代码总量。

冷 `/runs` 的就绪区间在本组样本中低于 B0，支持报告本次环境的观测改善。热 `/runs` 的区间重叠，不支持稳定提速结论。预测详情包含长尾，不能删除该样本后宣称稳定改善。后续产品决策应根据运行列表占比、首次表单使用频率和完整访问比例判断收益；本任务没有这些实际使用频率，因此不计算加权用户收益。

### 5.3 B2

B2 将图表/表单分成更细模块，但打包器也重排共享依赖，入口请求数增加。B2 相对 B1 的冷入口资源没有节省；首次表单与图表就绪中位数增加。B2 的预测详情新增资产略小于 B1，但节省量需要与入口额外资产、更多请求、长尾和完整访问成本共同判断。

功能模块在数据条件成立后才请求，存在额外模块获取与渲染阶段，具备增加串行等待的机制。当前实验没有对每个等待机制进行单独干预，无法把全部延迟差值归因于模块下载、某个包的解析或 React 调度；具体份额原因未查明。B2 的独立预览中位数较低，但预览样本范围与其他方案重叠，且该时间不包括已增加的表单首次加载成本。

原始修订的数值支持将 B1 保留为后续产品拆分的候选；最终建议等待修复重测。当前原始 B2 不具备额外收益。该判断基于字节、首次功能成本、完整访问资源与维护复杂度；没有以构建警告消失或任意百分比作为通过门槛。

## 8. 结论边界与验收状态
